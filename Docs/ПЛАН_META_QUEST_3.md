# ПЛАН: ПОДДЕРЖКА META QUEST 3

_Составлен 01.11.2026. Проект на **OpenXR**, а не на вендорском SDK — это главное, что делает
переход реальным._

---

## КОРОТКИЙ ОТВЕТ

**Да, проект можно сделать гибким под Quest 3.** И это дешевле, чем кажется, по одной причине:

> Проект **уже** читает контроллеры, кисти и позу через OpenXR и ищет устройства **по
> возможностям, а не по имени**. Это записано в коде с самого начала: «имена устройств у PICO
> отличаются от Quest/Vive, поэтому поиск идёт ПО ВОЗМОЖНОСТЯМ».

То есть фундамент переносимый. Нужен платформенный пакет Meta и несколько веток в местах, где
PICO и Meta расходятся.

**Оценка моей работы: 6–10 часов** (один рабочий день). Проверка на устройстве — за тестировщиком.

## ЧТО НАДО СДЕЛАТЬ (по шагам)

### 1. Добавить пакет Meta (15 минут)

**Unity Editor → Window → Package Manager → кнопка «+» (левый верхний угол) → Add package by
name…** → вписать:

```
com.unity.xr.meta-openxr
```

Пакет совместим с Unity 6000.5 — подтверждено документацией Unity.

**Почему не `com.unity.xr.oculus`:** он устарел, Meta перешла на OpenXR. Правильный путь — именно
`meta-openxr`, он даёт расширения Meta поверх OpenXR.

### 2. Настроить платформы (20 минут)

**Edit → Project Settings → XR Plug-in Management → вкладка Android:**

- поставить галочку **OpenXR** (уже стоит);
- внутри OpenXR — **Meta Quest Support** (появится после установки пакета);
- **PICO Support оставить** — обе платформы живут вместе, приложение само выберет нужную.

**Ключевая проверка:** в списке **Project Settings → XR Plug-in Management → OpenXR →
Interaction Profiles** должны быть ОБА профиля:
- `PICO 4 Ultra Touch Controller Profile` (уже есть);
- `Meta Quest Touch Plus Controller Profile` (появится с пакетом).

Если профилей два — контроллеры заработают на обоих шлемах без правок кода.

### 3. Ветка passthrough для Meta (2–4 часа)

Это единственное место, где нужна реальная работа.

**Сейчас:** `KvXrCapabilities.Passthrough()` спрашивает OpenXR-расширения вида `XR_FB_passthrough`,
`XR_PICO_passthrough` и т.д. — список уже написан.

**Что проверить:** Meta отдаёт passthrough через `XR_FB_passthrough`. Строка в списке есть, значит
определение должно сработать. Но **включение** сквозного вида у Meta своё — через
`MetaOpenXRPassthroughFeature` или `OVRManager.isInsightPassthroughEnabled`.

**План:** написать `KvMetaPassthrough` по образцу того, что уже есть для PICO, и включить его через
`KvXrCapabilities`. Тесты — 5–8 штук на выбор режима, как уже сделано для PICO.

### 4. Проверить масштаб и посадку (1–2 часа)

`KvXrMrRoom` и `KvXrMrPlacement` не зависят от вендора — они считают по реальному столу. Здесь
правок, скорее всего, не потребуется. Но проверить надо.

### 5. Собрать и отдать тестировщику (30 минут)

Сборка тем же скриптом `Tools/xr-build-apk-ascii.ps1`. **Один APK подойдёт и PICO, и Quest** —
если оба профиля взаимодействия в списке и в манифесте есть нужные расширения.

**Вероятная сложность:** манифест. Хук PICO дописывает свои метаданные; для Quest могут
потребоваться свои (например, `handtracking` для Meta). Это самая вероятная точка отказа — и
именно её надо смотреть первой при тесте.

## ЧЕСТНО О РИСКАХ

| Риск | Вероятность | Что делать |
|---|---|---|
| **API включения passthrough у Meta другое** | высокая | писать отдельную ветку — уже в плане |
| Контроллеры не подхватятся автоматически | средняя | проверить Interaction Profiles |
| Манифест Android не пройдёт проверку Meta | средняя | добавить метаданные в хук сборки |
| Кисти Meta работают иначе | низкая | `com.unity.xr.hands` общий для обеих платформ |
| Тестировщик соберёт не ту версию Unity | средняя | инструкция с точной версией (ниже) |

**Чего я НЕ могу:** проверить на Quest. Устройства нет. Всё, что сделаю — проверено тестами и по
документации, но **не на железе**. Это надо сказать тестировщику прямо.
