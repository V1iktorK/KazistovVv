## ЧАСТЬ 0. ЧТО УЖЕ ГОТОВО (не надо делать заново)

| Что | Где | Проверено |
|---|---|---|
| Режим VR/MR/AR выбирается по **возможностям**, а не по названию шлема | `KvXrPlatformModeSelector` | 13 тестов |
| Проба сквозного вида через **OpenXR** (без вендорского SDK) | `KvXrCapabilities` | 10 тестов |
| Три состояния ответа: **есть / нет / не удалось спросить** | там же | `Unknown` ≠ «нет» |
| `MrActive` требует **фактического** режима, а не только тумблера | `KvXrMrRoom` | 5 тестов |
| Метаданные PICO (сквозной вид, разрешения) в манифесте | `KvPicoManifestMetaData` | 3 теста |
| Требуемый масштаб стола **посчитан**: 0,069 по ширине | `KvXrMrPlacement.FitTableScale` | 7 тестов |
| Отсев нечисловых данных в XR-слое (8 мест) | разные | 16 тестов |
| Целостность сцен, конфигурация сборки, бюджет | разные | 20+ тестов |

**Ничего из этого переделывать не нужно.** Суббота — про проверку на железе.

## ЧАСТЬ 1. ПЕРВЫЙ ЗАПУСК: УЗНАТЬ, ЧТО УМЕЕТ ШЛЕМ

### Шаг 1.1. Собрать APK

```
powershell -ExecutionPolicy Bypass -File Tools\xr-build-apk-ascii.ps1
```

Сборка идёт ~70 минут. Пока идёт — можно читать часть 2.

### Шаг 1.2. Установить и запустить на надетом шлеме

Подключить по USB, затем:

```
powershell -ExecutionPolicy Bypass -File Tools\device-install-and-log.ps1
```

**Шлем должен быть НАДЕТ** — иначе сквозной вид не активируется, и проба честно ответит «нет».

### Шаг 1.3. Прочитать ДВЕ строки в журнале

Это главное действие субботы. Ищите в журнале:

```
[KvXr] возможности MR/AR: сквозной вид <есть|НЕТ|неизвестно> · якоря … · камера …
[KvXr] РЕЖИМ: <ВИРТУАЛЬНАЯ|СМЕШАННАЯ|ДОПОЛНЕННАЯ> РЕАЛЬНОСТЬ … · масштаб мира 1.000
```

**Возможны четыре исхода — и что делать в каждом:**

| Что в журнале | Что это значит | Что делать |
|---|---|---|
| `сквозной вид есть` + `СМЕШАННАЯ РЕАЛЬНОСТЬ` | 🎉 MR работает | перейти к части 2 (масштаб) |
| `сквозной вид НЕТ` | шлем не дал сквозной вид | проверить настройки шлема: «Сквозной вид» включён? Камера не закрыта? |
| `неизвестно` | проба не смогла спросить | **прислать мне журнал** — это моя недоработка в пробе, разберу |
| `РЕЖИМ: ВИРТУАЛЬНАЯ` | приложение честно в VR | нормально, если MR не нужен; иначе см. выше |

## ЧАСТЬ 2. МАСШТАБ: САМОЕ ВАЖНОЕ ДЛЯ MR

**Почему это критично:** в MR оператор стоит в СВОЕЙ комнате. Если виртуальный стол больше или
меньше реального — он не совпадёт с настоящим, и работать будет невозможно. Это не «косметика»,
это условие работы.

### Шаг 2.1. Посчитать, что должно получиться

```
масштаб = ширина реального стола / ширина виртуального
```

Для текущей сцены посчитано: **0,069** (виртуальный стол 14,4 юнита против реального 1,0 м).

**Но есть важная деталь:** у реального стола пропорция **10:7**, у виртуального — **3:2**.
Отношение масштабов по ширине и глубине расходится на **5 %**. Значит **единым коэффициентом
виртуальный стол к реальному не привести**: форма разная.

`FitTableScale` это распознаёт и пишет в строке «ПРОПОРЦИЯ НЕ СОВПАДАЕТ: единым масштабом не
приводится». **Если увидите эту строку — это не ошибка программы, а факт про модели.**

### Шаг 2.2. Что делать с этим фактом — ВАШЕ РЕШЕНИЕ

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Сделать реальный стол-стенд 3:2** (1,50 × 1,00 м) | виртуальный стол совпадёт точно | нужен новый стол или столешница |
| **B. Поправить виртуальный стол под реальный** (10:7) | ничего покупать не надо | правка геометрии сцены и, возможно, расстановки робота |
| **C. Оставить как есть и работать в VR** | MR не нужен сегодня | MR-сценарий откладывается |

**Я рекомендую A**, если MR — цель: виртуальная сцена — это модель, её можно подогнать, а реальный
стол — то, за чем оператор будет работать руками. Но решать вам: я не знаю ваших планов на стенд.

### Шаг 2.3. Подтвердить замер

Когда стол совпал, в журнале должно быть:

```
[KvXr] масштаб: по ширине <X> · по глубине <Y> · по высоте <Z> · пропорция совпадает, единый масштаб <S>
```

Числа `<X>`, `<Y>`, `<Z>` должны быть **близки друг к другу** (в пределах 5 %). Тогда форма совпала.

## ЧАСТЬ 3. ЧТО ПРОВЕРИТЬ ПОСЛЕ ЗАПУСКА

Проверять по порядку — каждый пункт опирается на предыдущий.

| № | Проверка | Признак успеха | Если не так |
|---|---|---|---|
| 1 | **Контроллеры видны** | две модели в руках, двигаются | см. карточку Б18 (причина на стороне рантайма PICO) |
| 2 | **Луч наводится** | линия от руки к панели, попадает в иконку | проверить «второй луч» в настройках |
| 3 | **Панель не уезжает** | стоит на месте, пока оператор смотрит | — |
| 4 | **Перенос окна** | панель едет за рукой по захвату | — |
| 5 | **Стол совпал** | виртуальная столешница на уровне реальной | часть 2 |
| 6 | **Стенды в MR** | виртуальные стенды СКРЫТЫ (реальная комната видна) | проверить тумблер «виртуальные стенды» |
| 7 | **Стенды в VR** | виртуальные стенды ВИДНЫ | это дефект 16.10.2026 — сообщить |

**Пункты 6 и 7 — прямая проверка того, что я чинил ночью.** В VR стенды обязаны быть видны
всегда; в MR — скрыты, если оператор не попросил обратное.

## ЧАСТЬ 4. ЧЕГО ЖДАТЬ НЕ СТОИТ

| Чего нет | Почему | Когда будет |
|---|---|---|
| **Пространственных якорей** | нет пакета якорей ни от Meta, ни от PICO | отдельная задача, нужен вендорский SDK или ожидание стандарта OpenXR |
| **AR на телефоне** | проект собран под шлем | AR-режим выбран в коде, но не проверен на телефоне |
| **Китайского текста в PDF** | встроенный шрифт только латиница | нужен файл CJK-шрифта (см. отчёт, раздел «решать вам») |

**AR-режим в коде есть, но не проверен.** Это честно: `Choose()` вернёт `Ar`, если есть камера и
якоря без сквозного вида. На шлеме такое сочетание не встречается, на телефоне — возможно. Пока не
проверено — считать неподтверждённым.
