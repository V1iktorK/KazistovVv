## 1. [НОВОЕ, БЛОКЕР] Шлем: приложение висит на разрешении камеры — VR не запускается

**Где:** PICO A9210 (`PA921DMGK4120784G`, Android 14, Vulkan). Проверено прогоном.

**Что видно в журнале:**
```
[KvEnv] ЗАПУСК: графика Vulkan · GPU Adreno (TM) 740 · модель Pico A921D · Android 14 / API-34
[KvAr] КАМЕРА: запрашиваю разрешение (до инициализации XR)
[KvAr] ИНТЕРФЕЙС: ПК-вид построен · меню 6 · дерево · инструменты · …
[KvAr] КАМЕРА: ждём разрешение (нажатий запроса: 0)   ← повторяется каждые 5 с, 8+ раз
```

**Суть:** AR-гейт камеры (`KvArCameraGate`, `EnsureCameraPermissionForAr`) срабатывает **в
VR-режиме на шлеме** и блокирует запуск. Диалог разрешения в шлеме нажать нечем → приложение
стоит вечно, VR не стартует.

**Почему это важнее остального:** именно поэтому VR/MR на шлеме **никто ни разу не проверял** —
до VR не доходит. Пока это не исправлено, пункты про VR/MR, кадры и панель в шлеме проверить
физически невозможно.

**Что сделать:** разрешение камеры — только для AR-ветки (планшет/телефон). В VR/MR на шлеме
камера-разрешение не требуется: PICO сам управляет доступом к камере через OpenXR. Проверить по
`KvArRuntime`/`KvXrPlatformModeSelector.Current`: если режим не `Ar` — гейт камеры не запускать
вообще. После запуска приложение должно дойти до `XrMain` и напечатать режим (VR или MR).

**Проверка гейтом:** `HEADSET` зелёный (нет «ждём разрешение», есть признак VR-режима).

## 8. [НОВОЕ 12.11, критично] Пауза во время движения превращается в аварийный останов «watchdog»

**Найдено чтением кода при разборе правок, подтверждено по композиции вызовов.**

Порядок, который исполняется в проде:

1. Оператор нажимает «Пауза» в движении → `TrajectoryExecutor.Paused = true`.
2. `Update()` на паузе вызывает `CheckStandingPose()` — это сделано намеренно (S44): робот стоит, но
   обстановка вокруг могла измениться, и это надо замечать.
3. `CheckStandingPose()` передаёт в `gate.ApproveStep(q, clearance, playhead, validator, out reason)`
   **текущий `playhead`**, а он на паузе не растёт (`PlayheadAfterFrame` возвращает его без изменений).
4. Первое же правило `ApproveStep` — «время должно идти вперёд»:
   `if (lastPlayheadTime > 0 && playheadTime <= lastPlayheadTime + 1e-6) → SafetyReason.Watchdog, return false`.
5. Отказ → `Stop(reason)` → **аварийный останов с причиной «watchdog: нет данных»**.

**Почему это дефект, а не задумка.** Причина в журнале ложная: watchdog жив, данные есть.
Оператор теряет движение, которое всего лишь хотел приостановить, и не может понять, что случилось.
Комментарий в `SafetyGate` прямо говорит, что смысл проверки на паузе — зазор и лимиты для СТОЯЩЕЙ позы,
а не ход времени; время на паузе заморожено осознанно.

**Правильное поведение:** на паузе проверяются живость данных, лимиты и зазор; правило «время вперёд»
к стоящей позе не применяется и учёт времени не портится (иначе после снятия паузы будет ложный
`Watchdog` на первом же кадре). Настоящая опасность на паузе (малый зазор, выход за лимиты, мёртвый
watchdog) обязана останавливать с ВЕРНОЙ причиной.

**Проверка (машинная, без чтения исходников):** последовательность «движение с растущим playhead →
кадр паузы с тем же playhead» не даёт останова; следующий кадр движения одобряется; зазор ниже порога
на паузе даёт `Clearance`.

## 9. [НОВОЕ 12.11] Правило «порог зазора один» заявлено, но не исполняется

Шапка `SafetyGate` (P1-16) объясняет, что три разных числа для одного понятия безопасности — дефект,
и заявляет: «Теперь порог один». В том же файле, в `ApproveStep`, исполняется буквально:

```csharp
if (clearance < minClearance * 0.5f) { reason = SafetyReason.Clearance; ... }
```

То есть предохранитель пропускает позу с зазором **вдвое меньше заявленного минимума**. Комментарий и
поведение расходятся; наладчик, читая шапку, получает неверную картину. Планировщик при этом строит
план с запасом `4/3` от `minClearance`, поэтому единый порог `minClearance` не отклонит ни один
корректно построенный план.

**Что сделать:** привести код к заявленному правилу (единый `minClearance`), либо, если половина нужна,
сделать её ИМЕНОВАННОЙ константой с объяснением, почему это безопасно, и поправить шапку.
**Проверка:** тест «зазор чуть выше `minClearance` проходит, чуть ниже — отклоняется»; тест обязан
краснеть, если в коде снова появится половина порога.
