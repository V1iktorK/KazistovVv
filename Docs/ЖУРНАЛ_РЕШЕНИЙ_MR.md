# ЖУРНАЛ РЕШЕНИЙ ПО MR

_Каждое техническое решение — с причиной «почему так». Без причины запись бесполезна: через месяц
её снимут как «непонятную правку»._
_План — `Docs/ПЛАН_MR.md`, факты — `Docs/ОТЧЁТ_MR.md`._

**Сессия:** S45, 02.11.2026.

## РЕШЕНИЯ

| Дата | Решение | Причина | Что проверено |
|---|---|---|---|
| 02.11 | Проба сквозного вида переписана на `OpenXRRuntime.GetEnabledExtensions()` (было — отражение в `OpenXRSettings.GetSettings()`/`ActiveFeatures`) | **Этих членов в OpenXR 1.15.1 нет.** Первая проба физически не могла ничего узнать и всегда возвращала «неизвестно» — поэтому режим всегда был VR. Список выданных расширений — единственный честный публичный источник, одинаковый для PICO и Meta | тест `CapabilityProbe_AsksRuntimeExtensions`; на устройстве ждём `XR_FB_passthrough` в списке |
| 02.11 | Отдельный слой `KvMrRuntime` с чистым выбором бэкенда `ChooseBackend(runtimeName, deviceModel, picoExtension, metaExtension)` | Вызов «не того» API — не ошибка компиляции, а чёрный экран на устройстве. Чистая функция проверяется тестом без шлема | 3 теста таблицей |
| 02.11 | Сквозной вид PICO: `EnableVideoSeeThrough` + проверки `isExtensionEnable` и `IsPassthroughSupported()` | Сеттер в пакете PICO «оптимистичный»: ставит флаг ДО проверки и игнорирует неудачу. Верить одному свойству — значит подтвердить то, чего нет | читал `PassthroughFeature.cs` (строки 43–126), тест `Passthrough_UsesVendorApi_NotBackgroundColor` |
| 02.11 | `IsPassthroughSupported()` вызывается только на Android и под `try/catch` | Это P/Invoke в `libopenxr_pico.so`, которая есть только Android/ARM64. В редакторе вызов = `DllNotFoundException` | тест `Failure_DoesNotThrow` |
| 02.11 | Включение фич OpenXR — инструментом `KvMrSetupTools` + перечитывание ассета | Состояние фич зависит от платформы: включённая для Standalone в APK не попадает (уже теряли контроллеры в §31) | метод печатает «ПОДТВЕРЖДЕНО ВКЛЮЧЕННЫМИ: 5 из 5» |
| 02.11 | Включаются ДВЕ PICO-фичи для passthrough: `PassthroughFeature` + `OpenXRExtensions` | `OpenXRExtensions` — `RequiredFeatureId` набора «PICO XR» и **ошибка валидации**, если её нет; только она даёт события пространственного меша | читал `PICOFeatureSet.cs`, `OpenXRFeatureBase.GetValidationChecks` |
| 02.11 | Реальные поверхности — через стандартный `XRMeshSubsystem`, а не `PXR_MixedReality.QueryMeshAnchorAsync`/`PXR_SpatialMeshManager` | (1) один код на PICO и Meta; (2) у `Query*Async` нет таймаута — `while(true){ PollFuture }` может повесить поток; (3) готовый менеджер ставит объект в `block.position`, не зная, локальны ли вершины, — риск двойного смещения | читал `PXR_MixedReality.cs`, `PXR_SpatialMeshManager.cs`, `MR_Plugin.cs`; тест `SurfaceRaycast_FiltersToRealWorldColliders` |
| 02.11 | Луч постановки фильтрует попадания по списку СВОИХ коллайдеров (`realWorldColliders.Contains`) | `Physics.Raycast` попадёт и в виртуального робота, и в панель. Менять слои проекта нельзя — это задело бы VR | тест + в MR печатается число коллайдеров комнаты |
| 02.11 | Робот переносится в корневой `KvMrWorld`, а НЕ остаётся ребёнком стенда | В сцене робот — ребёнок «Стенд_1_Стол». В MR стенд скрывается, и робот погас бы вместе с ним. Корень `KvMrWorld` не двигается ни с головой, ни с ригом — это и есть «не плывёт за головой» | тест `WorldRoot_IsNotChildOfRig` |
| 02.11 | Якорение — позой трекинга (мир в системе координат комнаты), без обязательного пространственного якоря | ТЗ (S3.2) разрешает: «через якорь **или через позу трекинга**». Блоки Б3/Б4 выполняются и так. Якорь нужен для сохранения между запусками — следующий шаг | тесты + проверка владельцем |
| 02.11 | Постановка по кнопке **A**, перехват в ОДНОМ месте — `KvXrActions.Confirm` | Курок уже несёт пять смыслов. Шестой смысл = дефект E-08 «одно нажатие — два действия». A — стандартное «подтвердить» в Quest/PICO. Перехват ровно один: израсходовали — обычное подтверждение не выполняется | тест `TryConsumeConfirm` в исходнике; в интерфейсе A не перехватывается |
| 02.11 | `DefaultPassthrough = 1` (сквозной вид по умолчанию ВКЛЮЧЁН) | Было 0 при комментарии «включён» — и `MrActive` был недостижим, вся ветка MR мёртвая. ТЗ S1.7: «режим определяется сам». При этом решает не тумблер, а факт возможностей | тест `Mode_IsAutomatic_PassthroughOnByDefault` |
| 02.11 | Масштаб: **не масштабировать мир**, сохранять авторский масштаб робота; «1:1» подтверждать замером габаритов | Модели роботов метрические (9 из 12 замеренных, 0,83–2,05 м), а виртуальные стенды — нет (14,4×10,08 м при высоте 0,98). Единым коэффициентом не приводится (план 14,4×, высота 1,256×). В MR стенды скрываются | таблица замеров в отчёте; тест `Placement_PreservesScaleAndLogsMeasuredSize` |
| 02.11 | Meta-ветка: `ARCameraManager`, БЕЗ `ARCameraBackground` и БЕЗ `ARSession` | По исходникам пакета 2.4.1: passthrough-слой создаёт камера-подсистема; `ARCameraBackground` на Meta не работает (`cameraMaterial == null`) и перезаписывает проекционную матрицу; `ARSession` не нужен, а на PICO мог бы подхватить Meta-сессию | читал `MetaOpenXRCameraSubsystem.cs`, `ARCameraBackground.cs`, `ARSessionFeature.cs` |
| 02.11 | Meta-фичи включаются ОТДЕЛЬНЫМ шагом и отдельной сборкой (сначала PICO) | Включение Meta-фич тянет обязательную Session-фичу (иначе ошибка валидации и падение сборки), правки манифеста и хук `OpenXRLifeCycleFeature` на PICO. Если включить всё сразу — нельзя отличить, что сломало | план этапов; отчёт фиксирует, что проверено на PICO до Meta |
| 02.11 | `KvXrPlatformModeSelector.EnsureApplied()` вызывается и из `KvXrMrRoom.Start` | Порядок `Start` между объектами Unity НЕ гарантирован: если MR-компонент стартует раньше рига, режим ещё `Vr` и MR не включится на шлеме, который его умеет | в отчёте — причина; проверяется строкой `РЕЖИМ:` на устройстве |
| 02.11 | Один экземпляр `KvMrSurfaces` (`Instance`), второй самоуничтожается | Два экземпляра построили бы две копии коллайдеров комнаты: луч видел бы комнату дважды, память вдвое | статический `Instance` + `Awake` |
| 02.11 | Определение режима ПЕРЕНЕСЕНО в корутину: ждать готовности XR (до 12 с), MR-комната ждёт факта «режим определён» (до 15 с) | **Найдено на живом шлеме:** на первом запуске PICO показывает диалог разрешений, приложение на паузе, `XRSettings.isDeviceActive = false`. Проба на первом кадре честно отвечала «сквозной вид НЕТ», и режим навсегда оставался VR — оператор разрешал доступ и видел виртуальную лабораторию при выданном `XR_FB_passthrough` | воспроизведено на устройстве: диалог → пауза → разрешение → строка «режим определён после готовности XR: XR активен» и режим MR |
| 02.11 | Автопостановка повторяется каждые 4 с (а не один раз через 3 с); запасной путь «на пол» — через 25 с; при появлении поверхностей робот переносится с пола на стол | Меш комнаты на устройстве приходит не мгновенно (а если шлем только что надели — через несколько секунд). Однократная попытка оставляла робота на полу навсегда | на устройстве: повтор идёт, в журнале «повторяю попытку каждые 4 с»; перенос с пола реализован и логируется |
| 02.11 | Для проверки на устройстве без надетого шлема на время отключено системное приложение `com.pvr.seethrough.setting` (`pm disable-user`) | Без этого PICO выводит его на передний план, и приложение не запускается вовсе (известная ловушка проекта). Проверка иначе невозможна без человека в шлеме | после проверки состояние устройства восстановлено (`pm enable`, тайм-аут экрана возвращён) |
| 02.11 | Фичи Meta Quest включены в ТУ ЖЕ сборку, что и PICO | Требование ТЗ — два шлема; отдельные сборки усложняют приёмку. Все AR-фичи Meta самогейтятся по возможностям рантайма, поэтому на PICO они безвредны — это и проверено на устройстве (режим MR работает) | сборка `Result: Success`, PICO: `РЕЖИМ: СМЕШАННАЯ РЕАЛЬНОСТЬ`, падений нет |
| 02.11 | Профиль контроллеров `OculusTouchControllerProfile` для Android **исключён** из сборки | Валидация PICO выдаёт ОШИБКУ «Only the PICO Touch Interaction Profile is supported right now» — с этим профилем сборка падает (`BuildFailedException: OpenXR Build Failed`). Проверено сборкой: включили профиль → падение, выключили → успех. На Quest ввод остаётся через уже включённые `OculusTouchControllerProximityProfile` и `KHRSimpleControllerProfile`; если не хватит — отдельная сборка под Quest с его профилем | два прогона сборки: с профилем — Failed, без — Success |
| 02.11 | Запасной источник стола — семантическая сцена PICO (`QuerySceneAnchorAsync(Table)`), с тайм-аутом (`Task.WhenAny` + `Task.Delay`) и ручной конверсией координат Box3D | Меш комнаты требует надетого шлема и разметки, а размеченные предметы дают стол параллелепипедом с габаритами. У пакета PICO поза СУЩНОСТИ переводится в Unity, а поза БОКСА — НЕТ (нужна инверсия Z), иначе стол окажется зеркально отражён. У нативных запросов нет тайм-аута — без него ожидание вечное | на устройстве: запрос выполнен, столов 0 (комната не размечена) — цепочка работает; код-тест на конверсию и тайм-аут |
| 04.11 | Запуск ПО УМОЛЧАНИЮ — VR; MR включается переключателем «Режим комнаты (MR)» в настройках шлема | Решение владельца по итогам теста: «сначала прога запускается как VR, но в настройках можно сделать MR». Рационально: MR без разметки комнаты работает запасным путём (пол), а VR проверен. Тумблер по-прежнему не единственный источник правды: `MrActive` требует фактического режима устройства | тест `Mode_DefaultsToVr_WithMixedRealitySwitchInSettings`; в журнале «применится после перезапуска» |
| 04.11 | Тепловая карта выключена по умолчанию (`heatmapOnByDefault = false`) | Владелец на тесте видел «шар и какие-то жёлтые элементы» — это тепловая карта: сфера вокруг робота, окрашенная по стоимости достижения, плюс жёлтое облако точек. Плюшка нужная, но не по умолчанию; включается `view.heatmap` (H) | функционал сохранён; сборка и тесты проверяют, что команда на месте |
| 04.11 | В стартовое меню добавлена строка режима (`ModeLine`), та же строка — в журнал при запуске | Владелец тестирует две программы (VR и MR) на одном шлеме; отличие должно быть видно в меню, а не только в журнале. Строка же печатается при запуске | тест на наличие `ModeLine` и «Режим комнаты (MR)» в панели |
| 04.11 | Предложение «разбить на микросервисы» ОТКЛОНЕНО | Приложение — единый Unity-проект (одна сцена, общие ассеты, IL2CPP/Android, один шлем). Дробление на сервисы: сломало бы работающую сборку и приёмку, добавило сетевую задержку и точку отказа на устройстве, а выигрыша не даёт. Модульность уже есть в коде (Xr/Core/Features/Trajectory) | — |
| 04.11 | Отменено «пусто при запуске»: `KvXrRig` больше не создаёт `KvXrSceneEmpty` | Владелец: «роботы пропали в VR версии». Причина — `KvXrSceneEmpty` (§42) каждый кадр гасил столы и роботов сцены, и в VR оставался пустой ангар. По ТЗ нужно «только робот, пульт и ангар» | тест `Scene_NoLongerHidesRobotsInVr`; на устройстве строка «СЦЕНА: роботы и стенды видны» |
| 04.11 | Чистый вид по умолчанию: `KvXrCleanView` гасит все шесть визуализаций ОДНИМ вызовом после подъёма служб | «Зоны включены» — не один флаг: визуализаций шесть (достижимость, лимиты, панель чисел, 2 теплокарты, зоны запрета, сингулярности), часть восстанавливалась из флагов сессии, а флаги по умолчанию применялись раньше создания служб. Один вызов после готовности — единственный надёжный способ | тест `CleanView_DisablesAllSixVisualizers` + `FlowBridge_AppliesCleanViewWhenServicesAreReady` |
| 04.11 | `KvXrHangarAnchor` ставит зал ТОЛЬКО по достоверной позе HMD и один раз | «Камера летает»: пока трекинг головы не готов, точка оператора бралась с объекта-камеры, и `Place()` метал зал каждый кадр — мир ездил сам. Проверка `fromHmd` стоит ДО перемещения корня | тест `HangarAnchor_DoesNotMoveWithoutHmdPose` (проверяет ПОРЯДОК строк) |
| 04.11 | Настоящий облёт простоя: `KvXrIdleOrbit` — 180 с покоя (контроллеры И голова), любое движение возвращает камеру; в MR выключен | Владелец: «камеру летающую оставь, но после продолжительного простоя; после шевеления контроллерами — нормальная камера». Настоящего облёта в шлеме не было (был баг выше), а штатный `IdleCameraBrain` сторож выключал. Свой облёт безопаснее: двигаем риг, а не камеру, и только в VR | тесты `IdleOrbit_LongIdleAndStopsOnControllerMovement`, `KvFrameBudgetTests` (поиск комнаты — один раз в `Start`) |
| 04.11 | ОБЛЁТ ПРОСТОЯ ИСПРАВЛЕН ПОСЛЕ ПОВТОРНОЙ ЖАЛОБЫ «всё равно камера летает»: порог 180 с → **900 с (15 минут)**, облёт ТОЛЬКО на надетом шлеме (`IsHeadsetWorn`: достоверная поза, высота 0,8–2,4 м, невырожденный кватернион), нажатие курков = активность, плюс выключатель «Облёт простоя: ВКЛ/выкл» в настройках | Журнал устройства показал точную причину: `ОБЛЁТ ПРОСТОЯ: включён после 180 с покоя` через 3 минуты после запуска, когда шлем ЛЕЖАЛ НА СТОЛЕ (контроллеры не двигались, позы головы не было) — камера начинала ездить сама, и владелец видел это, надевая шлем. 180 с — не «продолжительный простой»; на столе шлем обязан стоять на месте | тест `IdleOrbit_LongIdleAndStopsOnControllerMovement` (900f, `IsHeadsetWorn`); на устройстве проверяется строка «ОБЛЁТ ПРОСТОЯ: включён» только при надетом шлеме |
| 04.11 | В MR луч и метка постановки скрыты по умолчанию (`showAimByDefault = false`); чистый вид общий для VR и MR | «Сделай то же самое во второй реальности»: в MR те же визуализации, плюс луч/метка постановки — это подсказка, а не рабочий орган. Постановка идёт автопутём и по A, поэтому без них всё работает | тест `MrPlacement_HidesAimBeamByDefault` |

## ОТКЛОНЁННЫЕ ВАРИАНТЫ

| Вариант | Почему отклонён |
|---|---|
| «Масштабировать виртуальный мир коэффициентом 0,069, чтобы стол совпал с реальным» | План виртуального стенда больше реального стола в 14,4 раза, а высота — в 1,256. Единым масштабом не приводится: либо стол не той высоты, либо робот ростом с чайник. Стенды в MR скрываются |
| `ARCameraBackground` на Quest | Пакет 2.4.1 прямо пишет: на Meta Quest компонент «не оказывает никакого эффекта». Плюс перезаписывает `camera.projectionMatrix` |
| Создавать `ARSession` в сцене | Для passthrough не нужен; фича Session у Meta не самогейтится и на PICO может подхватить Meta-сессию |
| `PXR_SpatialMeshManager` из пакета PICO | Требует префаб с MeshFilter+MeshCollider, ставит объект в `block.position` (риск двойного смещения), пул на 200 объектов бросает исключение при переполнении |
| `PXR_MixedReality.QueryMeshAnchorAsync` | Нет таймаута: `while(true)` поллинга future может повесить поток; вендорский путь не работает на Quest |
| Постановка на курок / левый курок / правый стик | Курок уже несёт пять смыслов, левый курок — второй луч панелей, стик — телепорт. Любой дал бы «одно нажатие — два действия» (E-08) |
| Ставить робота в `tableCenter = (0,0,0)` (как было) | Это место оператора: робот оказывается внутри себя, видны только обратные грани |
| Править `XrMain.unity` ради MR-компонентов | SHA256 сцены закреплён тестом `KvXrS42Tests`; всё MR-оборудование создаётся в рантайме |
| Включать Meta-фичи в первой сборке | Риск сломать сборку/запуск на PICO, не имея возможности отличить причину |
