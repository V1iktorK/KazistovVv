# ЖУРНАЛ РЕШЕНИЙ ПО MR

_Каждое техническое решение — с причиной «почему так». Без причины запись бесполезна: через месяц
её снимут как «непонятную правку»._
_План — `Docs/ПЛАН_MR.md`, факты — `Docs/ОТЧЁТ_MR.md`._

**Сессия:** S45, 02.11.2026.

---

## РЕШЕНИЯ

| Дата | Решение | Причина | Что проверено |
|---|---|---|---|
| 02.11 | Проба сквозного вида переписана на `OpenXRRuntime.GetEnabledExtensions()` (было — отражение в `OpenXRSettings.GetSettings()`/`ActiveFeatures`) | **Этих членов в OpenXR 1.15.1 нет.** Первая проба физически не могла ничего узнать и всегда возвращала «неизвестно» — поэтому режим всегда был VR. Список выданных расширений — единственный честный публичный источник, одинаковый для PICO и Meta | тест `CapabilityProbe_AsksRuntimeExtensions`; на устройстве ждём `XR_FB_passthrough` в списке |
| 02.11 | Отдельный слой `KvMrRuntime` с чистым выбором бэкенда `ChooseBackend(runtimeName, deviceModel, picoExtension, metaExtension)` | Вызов «не того» API — не ошибка компиляции, а чёрный экран на устройстве. Чистая функция проверяется тестом без шлема | 3 теста таблицей |
| 02.11 | Сквозной вид PICO: `EnableVideoSeeThrough` + проверки `isExtensionEnable` и `IsPassthroughSupported()` | Сеттер в пакете PICO «оптимистичный»: ставит флаг ДО проверки и игнорирует неудачу. Верить одному свойству — значит подтвердить то, чего нет | читал `PassthroughFeature.cs` (строки 43–126), тест `Passthrough_UsesVendorApi_NotBackgroundColor` |
| 02.11 | `IsPassthroughSupported()` вызывается только на Android и под `try/catch` | Это P/Invoke в `libopenxr_pico.so`, которая есть только Android/ARM64. В редакторе вызов = `DllNotFoundException` | тест `Failure_DoesNotThrow` |
| 02.11 | Включение фич OpenXR — инструментом `KvMrSetupTools` + перечитывание ассета | Состояние фич зависит от платформы: включённая для Standalone в APK не попадает (уже теряли контроллеры в §31) | метод печатает «ПОДТВЕРЖДЕНО ВКЛЮЧЕННЫМИ: 5 из 5» |
| 02.11 | Включаются ДВЕ PICO-фичи для passthrough: `PassthroughFeature` + `OpenXRExtensions` | `OpenXRExtensions` — `RequiredFeatureId` набора «PICO XR» и **ошибка валидации**, если её нет; только она даёт события пространственного меша | читал `PICOFeatureSet.cs`, `OpenXRFeatureBase.GetValidationChecks` |
| 02.11 | Реальные поверхности — через стандартный `XRMeshSubsystem`, а не `PXR_MixedReality.QueryMeshAnchorAsync`/`PXR_SpatialMeshManager` | (1) один код на PICO и Meta; (2) у `Query*Async` нет таймаута — `while(true){ PollFuture }` может повесить поток; (3) готовый менеджер ставит объект в `block.position`, не зная, локальны ли вершины, — риск двойного смещения | читал `PXR_MixedReality.cs`, `PXR_SpatialMeshManager.cs`, `MR_Plugin.cs`; тест `SurfaceRaycast_FiltersToRealWorldColliders` |
| 02.11 | Луч постановки фильтрует попадания по списку СВОИХ коллайдеров (`realWorldColliders.Contains`) | `Physics.Raycast` попадёт и в виртуального робота, и в панель. Менять слои проекта нельзя — это задело бы VR | тест + в MR печатается число коллайдеров комнаты |
| 02.11 | Робот переносится в корневой `KvMrWorld`, а НЕ остаётся ребёнком стенда | В сцене робот — ребёнок «Стенд_1_Стол». В MR стенд скрывается, и робот погас бы вместе с ним. Корень `KvMrWorld` не двигается ни с головой, ни с ригом — это и есть «не плывёт за головой» | тест `WorldRoot_IsNotChildOfRig` |
| 02.11 | Якорение — позой трекинга (мир в системе координат комнаты), без обязательного пространственного якоря | ТЗ (S3.2) разрешает: «через якорь **или через позу трекинга**». Блоки Б3/Б4 выполняются и так. Якорь нужен для сохранения между запусками — следующий шаг | тесты + проверка владельцем |
| 02.11 | Постановка по кнопке **A**, перехват в ОДНОМ месте — `KvXrActions.Confirm` | Курок уже несёт пять смыслов. Шестой смысл = дефект E-08 «одно нажатие — два действия». A — стандартное «подтвердить» в Quest/PICO. Перехват ровно один: израсходовали — обычное подтверждение не выполняется | тест `TryConsumeConfirm` в исходнике; в интерфейсе A не перехватывается |
| 02.11 | `DefaultPassthrough = 1` (сквозной вид по умолчанию ВКЛЮЧЁН) | Было 0 при комментарии «включён» — и `MrActive` был недостижим, вся ветка MR мёртвая. ТЗ S1.7: «режим определяется сам». При этом решает не тумблер, а факт возможностей | тест `Mode_IsAutomatic_PassthroughOnByDefault` |
| 02.11 | Масштаб: **не масштабировать мир**, сохранять авторский масштаб робота; «1:1» подтверждать замером габаритов | Модели роботов метрические (9 из 12 замеренных, 0,83–2,05 м), а виртуальные стенды — нет (14,4×10,08 м при высоте 0,98). Единым коэффициентом не приводится (план 14,4×, высота 1,256×). В MR стенды скрываются | таблица замеров в отчёте; тест `Placement_PreservesScaleAndLogsMeasuredSize` |
| 02.11 | Meta-ветка: `ARCameraManager`, БЕЗ `ARCameraBackground` и БЕЗ `ARSession` | По исходникам пакета 2.4.1: passthrough-слой создаёт камера-подсистема; `ARCameraBackground` на Meta не работает (`cameraMaterial == null`) и перезаписывает проекционную матрицу; `ARSession` не нужен, а на PICO мог бы подхватить Meta-сессию | читал `MetaOpenXRCameraSubsystem.cs`, `ARCameraBackground.cs`, `ARSessionFeature.cs` |
| 02.11 | Meta-фичи включаются ОТДЕЛЬНЫМ шагом и отдельной сборкой (сначала PICO) | Включение Meta-фич тянет обязательную Session-фичу (иначе ошибка валидации и падение сборки), правки манифеста и хук `OpenXRLifeCycleFeature` на PICO. Если включить всё сразу — нельзя отличить, что сломало | план этапов; отчёт фиксирует, что проверено на PICO до Meta |
| 02.11 | `KvXrPlatformModeSelector.EnsureApplied()` вызывается и из `KvXrMrRoom.Start` | Порядок `Start` между объектами Unity НЕ гарантирован: если MR-компонент стартует раньше рига, режим ещё `Vr` и MR не включится на шлеме, который его умеет | в отчёте — причина; проверяется строкой `РЕЖИМ:` на устройстве |
| 02.11 | Один экземпляр `KvMrSurfaces` (`Instance`), второй самоуничтожается | Два экземпляра построили бы две копии коллайдеров комнаты: луч видел бы комнату дважды, память вдвое | статический `Instance` + `Awake` |

## ОТКЛОНЁННЫЕ ВАРИАНТЫ

| Вариант | Почему отклонён |
|---|---|
| «Масштабировать виртуальный мир коэффициентом 0,069, чтобы стол совпал с реальным» | План виртуального стенда больше реального стола в 14,4 раза, а высота — в 1,256. Единым масштабом не приводится: либо стол не той высоты, либо робот ростом с чайник. Стенды в MR скрываются |
| `ARCameraBackground` на Quest | Пакет 2.4.1 прямо пишет: на Meta Quest компонент «не оказывает никакого эффекта». Плюс перезаписывает `camera.projectionMatrix` |
| Создавать `ARSession` в сцене | Для passthrough не нужен; фича Session у Meta не самогейтится и на PICO может подхватить Meta-сессию |
| `PXR_SpatialMeshManager` из пакета PICO | Требует префаб с MeshFilter+MeshCollider, ставит объект в `block.position` (риск двойного смещения), пул на 200 объектов бросает исключение при переполнении |
| `PXR_MixedReality.QueryMeshAnchorAsync` | Нет таймаута: `while(true)` поллинга future может повесить поток; вендорский путь не работает на Quest |
| Постановка на курок / левый курок / правый стик | Курок уже несёт пять смыслов, левый курок — второй луч панелей, стик — телепорт. Любой дал бы «одно нажатие — два действия» (E-08) |
| Ставить робота в `tableCenter = (0,0,0)` (как было) | Это место оператора: робот оказывается внутри себя, видны только обратные грани |
| Править `XrMain.unity` ради MR-компонентов | SHA256 сцены закреплён тестом `KvXrS42Tests`; всё MR-оборудование создаётся в рантайме |
| Включать Meta-фичи в первой сборке | Риск сломать сборку/запуск на PICO, не имея возможности отличить причину |
