**После этого — Э3 MR (passthrough, масштаб, якорь), Э4 замеры под нагрузкой, Э5 долги (Git-коммит,
локализация), Э6 этапы 6–8.**

**Известные ограничения, найденные в этой сессии (важно для будущих):**
1. Unity batchmode требует свободной памяти: при 0,7–1,4 ГБ свободных редактор **зависает на
   IL Post Processor** и до компиляции скриптов не доходит. При 1,5–2 ГБ он работает (в этой сессии
   прогон прошёл). Перед прогоном закрыть MATLAB, браузер и Discord (держат ~7 ГБ из 15,8).
2. **Процесс Unity не завершается сам** даже после `Shut down.` — скрипты снимают его по таймауту
   и возвращают код 1 при полностью зелёных числах. Читать надо числа в логе и `editmode-*.xml`,
   а не код возврата; признак выполненной работы — `Shut down.` в логе и ноль `error CS`.
3. `Assembly-CSharp*.csproj` — генерируемые файлы с **явным списком** `<Compile Include=…>`:
   новый `.cs` не проверяется через `dotnet build`, пока Unity не откроет проект (или файл не
   добавят в список вручную). Дописано в `Docs/DEVELOPER_README.md` §4.2.

### 1.2 Что мешает приёмке прямо сейчас (два ограничения метода, не дефекты проекта)

   отдаёт **полностью чёрный кадр** (VR уходит прямо в композитор устройства).

   устройства** (строки `[KvXr]` + метрики `PxrMetric`).

### 1.3 Ключевое новое наблюдение, которого нет в документации

В журнале устройства при работающем приложении одна строка ввода:

```
[KvXr] XR-ввод: шлем есть · правый контроллер нет · левый контроллер нет · устройств в системе 0
```

**Но это ещё не доказательство дефекта.** Три причины, по которым вывод надо перепроверить
(и это первая задача Этапа 2):

1. строка печатается **один раз**, из `KvXrRig.Start()`
   (`Assets\_Project\01_Scripts\Xr\KvXrRig.cs:62`), то есть через ~5 с после запуска;
   контроллеры PICO появляются в системе позже и только когда их «видят» (взяли в руки / нажали);
2. запуск шёл **при не надетом шлеме** — устройство спало, трекинг стоял
   (`tracking_6dof_stopped: true` в `Logs\device-2026-10-08_1716.log`), а спящие контроллеры
   в систему не приходят;
3. `KvXrInputSource.Describe()` считает только устройства типа `XRController`, а сам поиск идёт
   по `InputSystem.devices` **без вывода состава** — по этой строке нельзя понять, были ли в системе
   другие устройства и какие (файл `01_Scripts\Xr\KvXrInputSource.cs:102-110`, `:198-225`).

### Этап 2. §32 «Управление»: контроллеры, луч, курок, телепорт, кнопки (2–4 прохода)

## 7. Правила работы (нарушение любого из них уже один раз стоило проекта)

1. **Работать в `C:\KazistovVv_Build`** (латинский путь), в конце — синхронизировать **изменённые**

   `_tests_parked_for_build` в корне проекта (уже потеряли 30 файлов).

6. **Не писать в документы «сборка погибла от сброса драйвера»** — сборка №1 снята намеренно.
7. **Порядок доказательства ([K5]):** сначала тест, который **падает**, потом правка, потом тест зелёный;
   «должно работать» — не результат. Пункт без строки в логе или снимка — **не проверен**.
8. **Десктопный режим не ломать** ([K3]): `MainScene`, ядро траекторий, State Machine — правки «снаружи».
9. **Каждая правка материалов кода → повторный прогон** `Tools\stage-a-verify.ps1`

10. **Перед длинной сборкой** — закрыть браузер и выключить аппаратное ускорение (Б7.1);
