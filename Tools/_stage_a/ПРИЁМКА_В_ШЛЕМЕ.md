# ПРИЁМКА В ШЛЕМЕ PICO 4 ULTRA — ЧЕК-ЛИСТ С ДОКАЗАТЕЛЬСТВАМИ (сессия §31)

_Составлен 08.10.2026. Пока шлема не было, приёмка была словами: «выглядит нормально».
Теперь у нас есть `adb`, и каждый пункт подтверждается ФАЙЛОМ: логом устройства и снимком экрана._

**Кто что делает.** Команды выполняет исполнитель (`Tools\device-install-and-log.ps1`);
в шлем смотрит владелец и отвечает по каждому пункту «вижу / не вижу».

---

## 0. Подготовка (один раз)

1. Шлем подключён кабелем USB-C, на нём включена **отладка по USB** (Настройки → Общие →
   О разработке → нажать «Версия ПО» 7 раз → Настройки → Общие → Разработчик → «Отладка по USB»).
2. Проверка связи: `pwsh -File Tools\device-install-and-log.ps1 -Mode Check`
   → должны появиться модель `A9210`, Android 14, SDK 34, `arm64-v8a`.

### 0.1 ВАЖНО: БЕЗ НАДЕТОГО ШЛЕМА ПРИЛОЖЕНИЕ НЕ РАБОТАЕТ (проверено 08.10.2026)

**Факт.** Приложение устанавливается и запускается, Unity поднимается, OpenXR и Vulkan
инициализируются — и через **1,5 секунды** система PICO усыпляет экран и приложение получает
`APP_CMD_STOP` (пауза). В журнале устройства это видно дословно:

```
I/ProximityPowerPolicyController: psensor gotoSleepFromPsensor canSleep=true,factoryTestNeverSleep=false
I/Unity: Handle cmd APP_CMD_STOP(15)
```

**Причина** — датчик присутствия (шлем не надет). Это нормальное поведение устройства, а не дефект
проекта.

**Обойти программно нельзя** (проверено): `setprop pvr.factorytest.never.sleep 1` и
`setprop persist.psensor.sleepmode 0` отклоняются — сборка production, `adb root` недоступен
(`adbd cannot run as root in production builds`). Фиксация экрана `svc power stayon true` тоже
не помогает: автосон идёт по датчику, а не по таймауту экрана.

**Что делать:** надеть шлем **или** закрыть датчик присутствия (положить шлем линзами вниз на
мягкое, либо накрыть внутреннюю часть тканью). После этого приложение работает и пишет свои
строки `[KvXr]`.

**Первый результат, который уже получен на устройстве (без приёмки глазами):**

| Факт | Строка в журнале устройства |
|---|---|
| APK установился | `Performing Streamed Install` → `Success` |
| Компания и продукт верные | `Company Name: KazistovVv`, `Product Name: KazistovVv` |
| Платформа распознана | `Device Model 'Pico A921D', OS 'Android OS 14 (API 34)'` |
| OpenXR поднялся | `[XR] Available Layers`, `XRGeneral Settings awakening...` |
| Vulkan работает (не падение) | `AdrenoVK-0: Engine Name: Unity` |
| Падений нет | ни одного `FATAL EXCEPTION` / `AndroidRuntime` |

Это **первый запуск собственного APK на живом шлеме** — и он прошёл без падения.

## 1. УСТАНОВКА И ЗАПУСК (исполнитель)

```
pwsh -NoProfile -ExecutionPolicy Bypass -File C:\KazistovVv_Build\Tools\device-install-and-log.ps1
```

Скрипт сам: находит `adb`, ждёт шлем, читает имя пакета **из APK** (`aapt`), ставит, запускает,
пишет лог `Logs\device-<дата>.log` и делает **три снимка экрана** `Logs\device-<дата>-t8/20/35.png`.

| # | Доказательство | Где смотреть |
|---|---|---|
| 1.1 | `Success` при установке | вывод скрипта |
| 1.2 | Приложение запустилось (не упало) | в логе нет `FATAL EXCEPTION`, `AndroidRuntime` |
| 1.3 | Ошибок в логе нет | раздел `ОШИБКИ И ИСКЛЮЧЕНИЯ` вывода скрипта |
| 1.4 | Снимки сделаны | 3 файла `.png` в `Logs\` |
| 1.5 | **Снимки разобраны числами** (розовое / чёрный экран / согласованность глаз) | `pwsh -File Tools\device-screenshot-check.ps1 -Image Logs` |

**Про снимки.** `Tools\device-screenshot-check.ps1` считает по пикселям: долю чёрных (пустой экран),
долю **пурпурных** (признак отсутствующего материала — «розовое»), долю цветных, средний цвет и
отдельно левый/правый кадр (признак проблемы со стерео). Вердикт печатается словами:
«экран пуст», «найдено розовое N %», «половины кадра различаются».

### 1.6 СНИМОК ЭКРАНА НЕ ПОКАЗЫВАЕТ VR-КАРТИНКУ (проверено 08.10.2026)

**Факт.** Когда наше приложение работает в VR, `adb exec-out screencap` отдаёт **полностью чёрный
кадр** (41 КБ, 100 % чёрных пикселей), хотя приложение живо и рисует 90 кадров/с. Чёрный кадр
получается и тогда, когда поверх показан интерфейс самих настроек PICO — снимки вида «427 КБ,
92,9 % чёрного, 40 оттенков» относятся именно к системному интерфейсу, а не к сцене.

**Причина:** VR-изображение уходит прямо в композитор устройства, 2D-поверхности для захвата нет.
Это **ограничение метода**, а не дефект проекта.

**Следствие для приёмки:**
* **техническая часть** проверяется **журналом устройства** (строки `[KvXr]` + метрики `PxrMetric`) —
  это доказательство, а не «кажется, работает»;
* **визуальная часть** (картинка, двоение, розовое, читаемость) — **только глазами владельца
  в шлеме**; автоматического снимка у нас нет.

## 2. СТРОКИ, КОТОРЫЕ ПРИЛОЖЕНИЕ ОБЯЗАНО НАПИСАТЬ

Это не пожелание: строки есть в коде, и каждая означает, что конкретная подсистема поднялась.
Проверяются поиском по `Logs\device-<дата>.log`.

| Строка в логе | Что доказывает | Файл кода |
|---|---|---|
| `[KvXr] Начинка XR-сцены: стенды обеспечены … роботов было N, стало M` | столы и роботы **построены в шлеме** | `KvXrSceneContent.cs` |
| `[KvXr] Робот для показа найден: …` | робот есть и найден для MR-постановки | `KvXrSceneContent.cs` |
| `[KvXr] Сторож камеры: …` | десктопный «облёт простоя» снят с камеры шлема | `KvXrCameraGuard.cs` |
| `[KvXr] <состояние рига>` (строка `Status`) | риг поднялся, стерео и целевые кадры заданы | `KvXrRig.cs` |
| `[KvXr] <описание источников ввода>` | найдены голова и контроллеры | `KvXrRig.cs` → `KvXrInputSource.Describe()` |
| `[KvXr] <описание слоёв MR>` | MR-комната посчитала масштаб и стол | `KvXrMrRoom.cs` |
| `[KvXr] ЧЕСТНОЕ ОГРАНИЧЕНИЕ: виртуальная геометрия проекта не метрическая…` | ожидаемое предупреждение (Б4/Б5) | `KvXrMrRoom.cs` |
| `[KvXr] Плоская панель: канвас интерфейса не найден за 5 с…` | **тревога**: панель не встала | `KvXrPanelAnchor.cs` |
| `[KvXr] В XR-сцене нет ни одного робота…` | **тревога**: начинка не построилась | `KvXrSceneContent.cs` |

## 4. ЕСЛИ ЧТО-ТО НЕ ТАК — СРАЗУ СНЯТЬ ДОКАЗАТЕЛЬСТВА

| Симптом | Что снять | Куда смотреть |
|---|---|---|
| Чёрный экран | лог + снимок | `FATAL EXCEPTION`, `AndroidRuntime`; рантайм OpenXR в логе |
| Розовые поверхности | снимок | материалы: `KvRenderPipelineTools` → «Аудит материалов» |
| Контроллеры не работают | лог | профиль контроллеров для Android (`KvDeviceTests.Android_HasControllerProfileForPico`) |
| Панель отсутствует | лог | строка `Плоская панель: канвас интерфейса не найден за 5 с` |
| Роботы не появились | лог | строка `В XR-сцене нет ни одного робота` |
| Двоение картинки | снимок | стерео-режим: должно быть `SinglePassInstanced` |
| Низкая частота кадров | числа | этап §34 (карточка Б6) |

**Правило проекта:** «должно работать» — не результат. Пункт без строки в логе или без снимка
считается **не проверенным**, и так и пишется в отчёте.

## 5. ЧТО ПОТРЕБУЕТСЯ ДЛЯ MR (этап §33, отдельно)

В приложении для сквозного вида сейчас **выключена** фича
`OpenXRCompositionLayersFeature` для Android (проверено 08.10.2026). То есть MR-режим
(`KvXrMrRoom`, тумблер прозрачности) включится, но реальная комната может не появиться:
это ожидаемое состояние, а не поломка. Работы по passthrough — отдельным этапом с включением
фичи и проверкой на устройстве.
